07
Interaction requirements
Non-negotiable behaviours. Motion clarifies state or causality, or it does not ship.
Motion — permitted
Console event append, 120 ms fade, newest last
Console collapse into run summary, 200 ms height
Drawer 240 ms slide from the right; sheet 280 ms from the bottom
Opportunity Delta count-up on first reveal only, 400 ms, tabular numerals so width never jumps
Milestone completion: node fill + rail colour, 300 ms
Accepted diff collapses into the resume preview, 200 ms
Behaviour — required
Opening a job never unmounts the run or loses scroll position
Every number over 24px has an inspectable derivation on the same screen
No AI-proposed text reaches a document without accept / reject
Assistant opens closed, scoped, and never on load
Engine failure states name the engine and confirm nothing changed
⌘K opens the assistant scoped to the current object; Esc closes any overlay
Accessibility
Every status colour is paired with a word — colour is never the only cue
Visible focus ring: 2px #6C63D8 at 2px offset, on canvas and on surfaces
Drawers and sheets trap focus and restore it to the trigger on close
Console is an aria-live polite region; it is not read event by event
prefers-reduced-motion: count-ups resolve instantly, slides become fades, nothing else changes
Motion — forbidden
Looping or decorative animation of any kind
Typing dots, thinking indicators, sparkles, glows
Confetti, trophies, streaks, XP, level-ups
Parallax or animated scenery
Any motion that runs while the user is reading dense data

11
Data contract — freshness & Opportunity Delta
Eight rules. The screens already behave as if these are true.
Every one of these is visible somewhere in the design, so a different answer is not a configuration change — it changes what a screen is allowed to say. Design-required means the screen breaks its own promise without it. Assumed means the design picked a defensible value and will follow whatever engineering decides instead.
#
RULE
WHAT THE DESIGN ASSUMES
WHERE IT IS VISIBLE
STANDING
01
Re-verification cadence
Every posting in the active target is re-checked once per scheduled run, plus on demand when the user opens Discover more than 6 hours after the last run. A run verifies live status, not the full parse.
Console event counts; “verified 2 h ago” stamps on every row
ASSUMED
02
Freshness bands
≤ 24 h reads normally in stone. 24–72 h renders apricot and the word stale . Beyond 72 h the posting is shown but excluded from every count. Three bands, because the design only has three treatments.
Discovery rows, Job Detail header, 12B stale banner
DESIGN-REQUIRED
03
Disappeared postings
A posting that vanishes from source is retained 48 h, labelled no longer listed at source , then dropped. It never disappears from under a user mid-session, and it stops counting the moment it is flagged.
Discovery row state; Delta drill-down list
ASSUMED
04
Delta is computed per run, never client-side
Both sides of the Delta are computed server-side at the end of a completed run and cached against that run id. The client renders a stored figure; it never derives one, so the same number cannot differ between two screens.
Home, One Fix Away, Roadmap — all read 12 → 20, +8
DESIGN-REQUIRED
05
A partial run never moves a number
A failed or cancelled run writes no Delta and updates no count. The last completed run stays authoritative and is labelled as such.
12B — “not counted toward your Opportunity Delta until a run completes”
DESIGN-REQUIRED
06
The audit set is stored, not reconstructed
Each Delta persists the explicit posting ids of its before and after sets, with each one’s closing date. The drill-down is a lookup. If the ids are not stored, the audit table is a guess and the guarantee that every number is inspectable fails.
One Fix Away audit table; Roadmap delta sidebar
DESIGN-REQUIRED
07
Predicted and realised are both kept
The predicted Delta is frozen at plan creation. The realised Delta is computed from the first completed run after the last milestone closes. Both persist, and the difference is explained by naming the postings that entered or left the set.
12E — realised +9 against predicted +8, with the reason
DESIGN-REQUIRED
08
Evidence-source staleness is separate
Source sync age is tracked per source and shown as stale past 14 days. It never blocks a run and never marks a posting stale — evidence freshness and posting freshness are different clocks and are never merged into one indicator.
Profile, Settings, 12F — “an engine problem never touches your evidence”
ASSUMED
